# POS responsive design decision

The POS uses one task-first layout with two responsive compositions:

- Below `768px`, the catalog is the primary surface. The cart is opened from a persistent bottom summary and uses a bottom sheet.
- Below `640px`, cashier utilities move out of the top bar into a full-height side sheet opened by an icon-only button beside the persistent cart summary. The sheet shows the current cashier and only actions whose feature, permission, and session requirements are satisfied; tablet and desktop retain the icon-only top bar.
- From `768px`, the cart remains visible beside the catalog so small landscape tablets can sell without switching surfaces.
- Product tiles are compact, keep a stable `16:9` media slot, and use the whole tile as the add target. Products with variants or modifiers keep their existing selection flows.
- A product already in the active cart keeps a visible primary ring and a live cart badge with its aggregated quantity across variants and modifier lines. The badge updates on every add, so rapid taps have immediate, persistent feedback without a toast interrupting barcode-heavy workflows. The same short confirmation tone plays only when an item actually enters the cart, whether it came from a tile, barcode, variant, modifier, weight, or amount flow; merely opening a picker does not signal success.
- POS product images are device-optional and default off. Image-free tiles prioritize product name, then price, category, and a numeric stock badge whose color communicates healthy, low, or out-of-stock state; the accessible label still names that state.
- At `320px` the catalog uses two columns. From `350px` through common 5-inch widths (`360–430px`) it uses three compact columns; larger widths use auto-fitting columns with a stable minimum tile width.
- Search and barcode scanning share one input. Searchable product and variant data is indexed when the catalog changes rather than rebuilt for every keystroke. A scanner submission uses the exact product or variant barcode/SKU first, clears the successful scan, and keeps the existing variant, modifier, and weight flows. `/` focuses and selects the search from outside editable controls, while `Escape` clears it; neither shortcut takes over an open dialog.
- Client catalog and online-order requests progress independently so a slow order board never blocks product rendering. The catalog response reuses the same category read for both category navigation and product presentation, and independent store plus warehouse/catalog checks execute concurrently without weakening their gates. Known POS roles use the already-authenticated role fast path; custom roles still require both `pos_access` and `checkout_create`. The loading state mirrors the final product grid rather than replacing it with an empty panel. A failed catalog request can be retried in place without reloading the page or losing the current cart and session; superseded catalog requests are aborted. Successful checkout refreshes inventory figures in the background while leaving the catalog interactive for the next sale; a background refresh failure keeps the last usable catalog visible. Returning to a visible POS tab refreshes a catalog older than one minute, with focus and visibility events sharing the same refresh window to avoid duplicate traffic; there is no continuous catalog polling while the POS is idle or backgrounded.
- Online-order refresh has one owner: it loads once when the POS mounts, then at a restrained interval only while the tab is visible. Requests never overlap, are aborted on unmount, and catalog/inventory refreshes do not trigger duplicate online-order reads.
- Payment methods remain direct actions. Credit, split payment, manager approval, and other guarded flows retain their existing confirmation steps.
- Weight and amount sales use one keyboard-friendly dialog: explicit mode switching, a large unit-aware numeric field, kilogram presets, live quantity and total summaries, and a persistent cancel/confirm footer. The focused field follows visual-viewport resizing so it stays visible above mobile keyboards, and the keyboard's done action submits the form. Gram input and previews remain in grams rather than being presented as kilograms.
- Receipt success prioritizes browser print, WhatsApp, and a new sale. A4 and USB printing remain available as secondary actions.
- When the cart is non-empty, cashier actions expose a manual draft receipt preview before checkout independently of the post-save receipt preference. It supports browser/USB printing and WhatsApp (including a one-time phone), labels the output as not saved, and never creates an order, mutates inventory, or clears the cart. The `receipt_printing` preference continues to control the automatic post-save receipt flow.
- Receipt preview dialogs open without auto-focusing the optional WhatsApp phone field, keeping the receipt visible and avoiding an unsolicited mobile keyboard. The preview compacts only after the cashier deliberately focuses that field.
- The active-session action bar exposes a searchable session invoice history. It loads a lightweight newest-first list with customer, phone, payment method, and visible exceptional order/payment states; search matches invoice number, customer name, or phone. Full details load only for the selected invoice, which the cashier can preview, print, or share. Server-side checks bind every lookup to the current store, cashier identity, and active session; a newly completed sale refreshes the history without a page reload.
- Session closing is a single two-step flow followed by an explicit result state: review the live session summary, count and confirm cash, then print the closing report or return to POS. The summary separates all-channel sales overview from the cash-drawer calculation, hides zero-value deductions and empty expense detail, and keeps the expected cash as the calculation's emphasized result. Its orders, cash payments, refunds, expenses, and supplier payments are aggregated in one RLS-respecting database function call, backed by session and payment lookup indexes. Closing is blocked when the live summary cannot load, and the server rejects a stale expected-cash snapshot so the cashier must review changed totals before trying again. The cash amount is validated in the client, Server Action, service, and database.
- Each cashier owns an independent open session per store. A partial database uniqueness index prevents double taps or concurrent devices from creating duplicate open sessions for the same cashier; a racing open request reuses the winning session and refunds its duplicate opening-float withdrawal. Session reconciliation temporarily falls back to equivalent RLS-scoped queries when the optimized database function has not reached a deployment yet.
- POS access is scoped by organization, store, signed-in user, and active cashier only. Device registration and pairing are not part of login or readiness. Session `device_id` remains nullable solely for historical compatibility, and held carts follow the cashier across browsers within the same store.
- Closing does not open a confirmation dialog on top of the close dialog. A vault-transfer failure is shown as a recoverable post-close state with an idempotent retry; it must never be presented as if the session itself were still open. Closing form state is discarded whenever the POS dialog is dismissed and reopened. Dialog visibility is scoped to the session ID that opened it, so a newly opened session can never inherit the previous session's close dialog.
- Session invoice summaries and opened receipt payloads are cached only in the active POS screen for instant repeat access. A completed sale invalidates the list automatically, while a visible manual refresh control re-syncs external status/payment changes and clears receipt-detail cache.
- Receipt line items isolate bidirectional product names from numeric quantity and price details. Compact previews allow two name lines and use tabular totals, preventing Arabic names from being clipped or reordered when the operator UI is English; the browser-printed receipt uses the same structure.
- Reopened saved receipts preserve the selected variant name, original sale unit, weight/amount mode metadata, price tier, wholesale flag, and item modifiers. Visible receipt, browser/USB print, and WhatsApp formats include variant and modifier details so session-history copies remain faithful to the sale.
- Reopened voided or refunded sales carry an explicit exceptional-status banner in the preview and browser print, plus a status marker in USB and WhatsApp text. A historical copy must never look like an active completed sale.
- When a receipt has no customer phone, WhatsApp accepts a one-time phone number. It is normalized for the link and is never persisted to the customer record.

Compact means reducing chrome, gaps, and repeated descriptions—not shrinking interactive controls. All POS changes must preserve RTL/LTR parity, visible focus, at least `44px` touch targets for controls at every breakpoint, safe-area padding, and the existing checkout, inventory, permission, loyalty, promotion, and receipt contracts.

Mobile height follows the live visual viewport (`dvh`, with `svh` fallback) and uses `interactive-widget=resizes-content`, so layouts resize when browser chrome or the keyboard changes. Browser URL chrome cannot be forcibly hidden by a web page; permanent URL-free operation uses the existing standalone PWA installation. Physical notch and home-indicator insets must remain protected with `env(safe-area-inset-*)` and must not be visually “compressed”.
